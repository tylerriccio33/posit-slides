I’m trying to install python…

  • What’s an interpreter?

Cold open, present tense, first person: pip, conda, pyenv — pre-uv world. What’s an interpreter? What’s a path? What even is an IDE? Land the joke — everyone in the room who has installed Python has a version of this story. Turn it: the first impression is not a footnote. It sets the tone for everything that follows. Note: Don’t let this become the whole talk — plenty of talks exist just on Python packaging. One beat, then move.

Takeaway:

APIs matter.

Thesis:

Choose the easiest thing.

Thesis The hot take: APIs matter more than speed State it plainly and let the rest of the talk earn it: the API decision should come first — ahead of performance, cost, and support — because it’s the one factor that determines how much friction the humans on the team absorb.

The easy migration

I want to outline what goes into an easy migration

Chapter One: Getting started fast

  • Early wins matter
  • First impressions matter

Pick the API that lets people write real code on day one, before they’ve mastered environments, classes, or types. Imagine you get a cocktail at a new spot, and the cocktail is horrible. You probably associate this place as not being good, I know so because I did this. When I went back I got a fantastic cocktail, and I’m a regular there now. Friction at the start compounds. A team that’s writing working code in week one builds momentum a team still debugging pip does not.

Getting Started Fast = “Can I be productive immediately?”

  • dplyr
  • Polars
df %>%
  group_by(group) %>%
  summarize(
    revenue = sum(revenue),
    paid = sum(revenue[status == "paid"])
  )
df.group_by("group").agg(
    pl.col("revenue").sum(),
    pl.col("revenue")
      .filter(pl.col("status") == "paid")
      .sum()
)

Pillar One: Getting Started Fast Make this about activation energy and the first 30 minutes/day. Your selector/aggregation example is good here, but I’d use the simplest possible version. You don’t want to explain the code; you want the audience to recognize it instantly.

Chapter One: Getting Started Fast Early wins matter. First impressions matter. Pick the API that lets people write real, useful code on day one. Don’t make the first lesson environments, classes, types, or package management. Friction at the start compounds.

Then your cocktail analogy works here. The core idea is: The first experience determines whether people keep going. The code demo should therefore show “I just learned this and immediately accomplished something.”

The audience takeaway is simply: “Holy shit, I can already do real work.” Don’t get into the philosophy yet.

Pillar one conclusion:

APIs should be treated as customer experience. Treat the consumer like a customer.

APIs should be user first, many are, but many aren’t. Frameworks that have user friendly APIs will pay dividends in the beginning as people come up to speed on the other more complicated pieces of the language.

Pillar Two: Keep the same shape of thought

  • Easy syntax is a virtue
  • Import your philosophy

Other options leveraged highly verbose or typed languages, introducing layers of complexity and friction We chose Polars because its expression-based API preserved the dplyr way of thinking about data.

Code snippet on similarities in syntax/philosophy

sum(revenue[status == "paid"]) becomes:

pl.col("revenue")
  .filter(pl.col("status") == "paid")

Same thought. Different language.

Pillar Two: Keep the Same Shape of Thought This should be about transfer, not onboarding. The question becomes: After I know how to use it, does the system let me keep thinking about data the way I already do? This is where your functional-expression argument belongs.

I’d restructure the points: Pillar Two: Keep the Same Shape of Thought Don’t make people relearn how to think about data. Easy syntax is a virtue. Import the philosophy, not just the syntax. We wanted an API where operations compose as expressions over columns. The existing dplyr mental model transfers: select → transform → filter → aggregate. No need to first learn OOP, strong typing, or imperative loops.

Then your selector/conditional aggregation example becomes much more powerful here than on Pillar One.

Then explicitly call out: Same thought. Different language. That’s the actual migration story.

Pillar two conclusion:

Some days, you don’t need to learn anything new.

Asking people to migrate is like information overload, they’re going to learn a ton and it doesn’t all have to be at once. Do you take calc 4 before calc 1? No.

When people are comfortable, they’ll move on to the fancier stuff and make more informed decisions.

Pillar Three: Morale

  • Maintain early consistency
  • Reduce fear

Early consistency improves code sharing and other key abilities, and increases efforts for collaboration. By choosing something easy, you can maintain morale and keep people engaged during what is likely a stressful time

Maintain Morale → Can the team keep moving without the migration becoming psychologically expensive?

Pillar Three: Maintain Morale I’d phrase the slide roughly like this: Consistency reduces fear. Maintain early consistency across the team. A migration is already disruptive. Don’t make every developer’s experience different. Shared idioms make code easier to read, review, share, and debug. Early wins build confidence; confidence keeps people engaged. Choose the tool that lets people feel competent before they feel expert.

I would also change “early consistency” “Early consistency” is a little ambiguous. It sounds like you’re saying write consistent code immediately, which isn’t really the deeper point.

Pillar Three: Reduce Fear Don’t make the migration harder than it already is. Keep as much of the team’s existing mental model as possible. Shared idioms create consistency in code reviews, debugging, and collaboration. Early successes create confidence; confidence creates engagement. Every unnecessary conceptual change increases the psychological cost of migration.
